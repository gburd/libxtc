# vexec vs VDBE -- analytic A/B results

Generated by `run_vexec.sh` (`vexec_bench.c`): the same query through
SQLite's VDBE, the single-threaded vectorized executor, and the
morsel-parallel vexec at 1/2/4/8 worker loops.  Every result is first
checked for correctness (row count == VDBE) before timing.

## Representative run (500k rows, best-of-3, an 8-core dev box)

| query                                   | vdbe | vexec 1t | 2w | 4w | 8w |
|-----------------------------------------|-----:|---------:|---:|---:|---:|
| count(*) WHERE a > 500000               | 1.00 | 0.41 | 0.31 | 0.38 | 0.37 |
| count/sum/min/max (full aggregate)      | 1.00 | 0.56 | 0.61 | 0.84 | 0.88 |
| GROUP BY g (64 groups)                  | 1.00 | 0.86 | 1.24 | 1.76 | 1.97 |
| t JOIN u ON t.g = u.j                   | 1.00 | 0.22 | (serial only) | | |

(numbers are speedup vs the VDBE baseline; >1 is faster.)

## What this shows -- and the honest ceiling

The GROUP BY aggregation **scales with workers** (1.24x -> 1.76x ->
1.97x), which is the V2/V3 morsel-parallel claim doing real work the
single-threaded VDBE cannot: each worker aggregates its own morsels into
a local hash table and a final Combine merges them.

But vexec is **slower than the VDBE single-threaded** on every query,
and parallelism only catches up.  This is a direct, expected consequence
of the V0 design decision: vexec's row SOURCE is the reference engine's
own cursor -- each worker opens a `sqlite3_stmt` and steps it.  So vexec
pays the FULL VDBE cost to produce each row PLUS its own per-row
materialization and expression evaluation; it cannot be faster serially
because it does strictly more work layered on top of the VDBE.
Parallelism wins only when the EXTRA work (aggregation, a hash join's
build/probe) parallelizes enough to overcome that surcharge -- which is
why GROUP BY scales and a bare filtered count does not.

That source choice was deliberate and correct for V0-V5: it made MVCC
visibility, version decoding, and type/affinity identical to the VDBE
for free, so the differential oracle could prove correctness without
re-deriving any of it.  The cost is the performance ceiling measured
here.

## The next step to actually beat the VDBE

To win serially (and have parallelism multiply a real win rather than
claw back an overhead), vexec must read rows **directly from the xstore
B-tree** -- the cursor primitive sqlxtc already has -- decoding columns
with the engine's own record codec and applying MVCC visibility itself,
instead of stepping a `sqlite3_stmt`.  That removes the VDBE from the
hot path entirely; the morsel cursor then slices the B-tree key range
directly (the O(1) parked-cursor resume makes a morsel a [start, count]
slice).  This is the storage-native source the doc's "the storage reads
are already async ... I/O latency overlaps compute for free" paragraph
assumes, and it is the work that turns the parallel-aggregation scaling
shown above into an across-the-board win.
